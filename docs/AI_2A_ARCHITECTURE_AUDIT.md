# TalentScope.ai — AI-2A Architecture, Firestore, and AI Engine Audit

**Scope:** static source review of the checked-out repository. No Firebase project, provider, Gemini endpoint, browser login, or production dataset was contacted. This is not a deployed-environment verification.

## Executive assessment

The application is a React client backed by a FastAPI API. The backend verifies Firebase ID tokens, reads and writes application state through Firebase Admin/Firestore, and has local SQLite reference-data and legacy market stores. Market collection is a separate opt-in backend path. The Core Intelligence API combines stored observations, reference catalogs, deterministic analytics, capability/intent orchestration, conversation persistence, and optional Gemini explanation. The code supports multiple named product surfaces, but a visible route or screen does not establish that the feature has validated data, production configuration, or a deployable rules/index setup.

No evidence in the checked-in repository establishes production Firestore contents, production security rules, active scheduled jobs, actual provider quotas, or deployed service configuration. `firebase.json` configures local emulators and an indexes file but does not name a Firestore rules file. No `firestore.rules` file was found in the repository root. Rules deployed in Firebase therefore remain unknown and require owner verification.

The current working tree contains substantial pre-existing modifications across backend, frontend, tests, Firebase config, and untracked emulator/audit files. This audit adds only this Markdown document; it does not stage, reset, revert, or otherwise alter those changes.

## Architecture and trust boundaries

1. **Client:** React routes render individual, employee, and company screens. API wrappers call FastAPI; Firebase client code is present for authentication. The frontend's emulator configuration is distinct from backend Admin configuration and both must point to the same demo project and local endpoints for a safe local run.
2. **API:** `backend/app/api/router.py` mounts health, auth, onboarding, market, skills, company-relationship, and Core Intelligence routes. Protected routes use `get_current_user`; `backend/app/api/dependencies.py` verifies bearer ID tokens with revoked-token checking and resolves company membership using trusted user/company/member records.
3. **Application data:** Firestore stores user profiles, company records and membership subcollections, invitations/requests, market jobs and observations, collection runs, raw provider archives, calculations/evidence references, conversation state, and Gemini quota reservations. `ReferenceDataStore` is local SQLite for imported taxonomies/adoption reference datasets. `MarketDataStore` is a legacy SQLite market implementation and should not be conflated with the Firestore observation source of truth.
4. **Collection boundary:** `market_collection_service.py` selects only configured and credentialed supported collectors. The provider classes can make outbound calls when the collection operation is invoked. The route `/market/admin/collect` is an operational write/collection surface; its authorization and deployment exposure require an environment-specific review.
5. **AI boundary:** planning, entity resolution, capability checks, deterministic analytics, and answer orchestration are backend services. The LLM explanation service may call Gemini when enabled and reserves quota in Firestore. Its presence does not imply that every answer is generated by a model or that historical forecasting is trained/ready.

### Signal interpretation

- **Job-posting demand:** JSearch and Adzuna collectors normalize sampled postings into demand observations. Results are provider/query-window samples with pagination, quota, query, geography, and collection-completeness limitations. The provider's total universe and denominator cannot be assumed. A true zero requires a verified complete sampling frame; missing/failed collection is not zero demand.
- **Developer adoption:** GitHub activity is a developer/repository signal and must stay separate from job-posting demand. Quarterly source periods must not be silently converted into monthly hiring observations.
- **Technical interest:** Stack Exchange, Hacker News, npm/PyPI or similar ecosystem activity, when configured, represents attention/use/adoption proxies according to each metric, not hiring. Each source needs its own metric, unit, query/panel, coverage and denominator contract.
- **Pageviews:** Wikipedia pageviews measure page attention, not employers, vacancies, or applicant demand.
- **Occupational reference:** O*NET/ESCO taxonomies and crosswalks provide standardized occupational/skill context, not temporal demand observations.
- **User/company profile:** Onboarding skills, priorities, workforce counts, and job preferences are declarations or product context, not independently verified market observations.

## Readiness and principal gaps

The current backend already contains observation identity, source/panel metadata, collection run tracking, comparability/period validation, quality checks, and readiness gates. Reuse these contracts; do not create a second series engine. The AI-1A audit implementation accepts explicitly supplied CSV, JSON/JSONL, and SQLite snapshots with the supported canonical schema and blocks unsupported Firestore export formats instead of guessing.

The preceding AI-1B assessment found no approved nonempty observation snapshot available for offline review; the checked local SQLite observation table was empty. That evidence supports only “no approved local snapshot was available in that assessment,” not “production has no data.” The current review did not inspect Firebase or production records.

**Demand forecasting remains blocked** because no approved historical demand panel was evidenced locally with at least 24 consecutive comparable completed monthly observations, consistent source/query/geography/unit/denominator, adequate collection completeness, and a holdout evaluation against the seasonal-naive baseline. The minimum observation count alone is insufficient. Current posting snapshots cannot be backdated into history.

**Skill Half-Life remains blocked** until a single normalized signal series has at least 36 consecutive completed monthly observations and a statistically supported decline. Adoption, interest, and hiring-demand signals cannot be mixed to reach that threshold.

Other material gaps visible from source/configuration:

- No checked-in Firestore security rules are available for review; deployed rules are unknown.
- Firebase indexes are declared locally, but deployment state is unknown.
- Repository documentation describes the scheduler as disabled by default/not provisioned; actual deployed scheduler/jobs must be confirmed by the project owner.
- Provider coverage, credentials availability, quotas, supported geographies, provider terms, retention, and historical/backfill rights are deployment/contract questions, not inferable from source.
- Raw archives and conversations contain potentially sensitive data. Retention, least-privilege access, deletion, and incident-review ownership need explicit operational policy.
- Existing capability catalog “available” indicates code handler status; it is not evidence that data or runtime configuration meets the capability's request-specific readiness requirements.

| O*NET/ESCO and other reference data | **Reimportable reference** | Keep source release/version, license/terms, checksum and ingestion log. Replace only with a versioned import and compatibility check. |

| Local emulator/test data | **Disposable in isolation** | Keep demo project IDs and emulator hosts explicit; prevent local fixtures from being exported as real user or market data. |

## Phased rebuild / hardening plan

### Phase 0 — Owner decisions and evidence

1. Project owner identifies the authoritative Firebase project/environment and supplies a rules/index deployment review through their approved process; do not use application credentials for this audit.
2. Security/privacy owner determines whether Auth request metadata or account data exposure warrants incident response, retention, or notification actions. Provider/legal owner confirms collection rights and retention for each data source.
3. Data owner supplies an explicitly approved, minimized offline snapshot and a manifest (origin, time range, export method, schema/version, checksum, redaction status, approval). Do not accept native Firestore export artifacts unless a supported, verified importer is provided.

### Phase 1 — Preserve canonical contracts

1. Keep `MarketObservation`, stable observation identity, series comparability, period validation, quality/readiness gates, fetch-run records, and audit tooling as canonical contracts.
2. Require provenance for each observation: `observation_id`, `source`, `signal_type`, `metric`, `unit`, `value`, `geography`, `observed_at`, canonical period, `query_id`/panel version, `fetch_run_id`, `data_origin`, collection completeness/quality and denominator semantics.
3. Require source-specific validation adapters. Reject missing units, incompatible query/panel changes, duplicate periods, contradictory identity, fabricated periods, synthetic values, and incomplete collections masquerading as zero.

### Phase 2 — Offline import and acceptance

1. Use the existing readiness audit's supported CSV, JSON/JSONL, or canonical SQLite input only. Record the explicit input path, checksum and schema; keep it read-only.
2. Review only aggregate validation output. Quarantine rejected rows and explain counts/reasons without printing raw IDs, provider payloads, or user fields.
3. Compare imported eligible series by source, signal, geography, unit, query/panel and period. No cross-source summation or backfilling across missing months.

### Phase 3 — Collection foundation (not authorized in this audit)

1. After owner approval, select a source with documented historical access rights and a stable, defined sampling frame. Prefer an explicitly licensed, historical postings dataset if its terms permit analysis; otherwise collect provider snapshots prospectively under approved quotas/terms. Do not claim sampled provider coverage is the whole labor market.
2. Schedule collection only after a separate deployment approval. Each scheduled run needs an idempotent run ID, query/panel version, requested/received/rejected/filtered counts, pagination/coverage status, quota/rate-limit status, start/end times, and terminal success/partial/failure state.
3. Use stable source-native record identifiers plus canonical observation identity for deduplication. Define how edited/reposted listings are treated, how expired/removed jobs are handled, and how same posting across providers is reconciled without double counting.
4. Publish a monthly period only after the collection window closes and required pagination/completeness checks pass. Missing or failed periods remain missing; do not insert zeros unless source semantics prove a complete zero.
5. Monitor lag, duplicate rate, panel drift, geography/category coverage, denominator completeness, failure rate, provider limits and retention. Page an owner for persistent failures; record failures rather than silently skipping them.

### Phase 4 — Readiness re-evaluation, no premature training

1. Re-run offline readiness evaluation as consecutive completed months accumulate; preserve fixed gates: 24 months plus seasonal-naive holdout evaluation for demand forecasting, 36 normalized monthly periods plus supported decline for half-life.
2. Before forecasting, compare holdout metrics with seasonal-naive baseline and report by series/panel. Keep the holdout chronological and untouched by fitting/tuning.
3. If collection policy, provider query, sampling, geography, unit, or denominator changes, start/mark a new panel and reassess comparability rather than silently joining it.
4. Train only after an owner-approved dataset passes quality, provenance, legal, comparability, baseline, and leakage checks. A readiness pass is necessary, not a guarantee of model utility.
